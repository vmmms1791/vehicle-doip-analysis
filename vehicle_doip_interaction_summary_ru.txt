## 2. Анализ пользователя взаимодействия VNCI 6154A по DoIP с VW ID.7
- Сетевая топология: при работе VNCI в режиме DoIP создаётся изолированная VLAN.
  - IP‑адрес ПК: 192.168.13.240
  - IP‑адрес устройства VNCI: 192.168.13.69
- С помощью VCTool обнаружен реальный IP‑адрес шлюза VW ID.7: 192.168.13.241.
- Автомобиль отвечает на стандартные диагностические порты DoIP (TCP/UDP 13400) согласно ISO 13400.
- Защита платформы VW MEB:
  - Стек DoIP шлюза находится в спящем режиме; обычное сканирование сети (arp -a или сетевые утилиты) не показывает адрес автомобиля.
  - Шлюз пробуждается после получения триггера: либо сигнал 12 V на линии OBD (контакт 8), либо широковещательный UDP‑запрос Vehicle Identification Request.
  - Ручные запросы Routing Activation Request через текстовые утилиты (Packet Sender) завершаются ошибкой «Could not connect» или сбросом сессии, поскольку:
    * Блоки VAG на платформе MEB жёстко контролируют таймауты соединений.
    * Требуется строго бинарный формат пакета (без лишних ASCII‑символов вроде CR/LF).
    * Параллельный запуск другого диагностического ПО может блокировать порт.
- Рекомендованный путь чтения данных автомобиля без ODIS:
  - Автоматизация на Python с библиотеками `udsoncan` и `doipclient`.
  - Поддержание открытой TCP‑сессии, установка логического адреса тестера (например, 0x1000 для эмуляции ODIS), передача чистых UDS‑запросов (ISO 14229) для чтения VIN (0xF190), параметров батареи, напряжения ячеек, кодов неисправностей и т.д.

## 3. Уточнение относительно активации Ethernet (пин 8 OBD) и пробуждения CAN‑шины
- Формулировка «сигнал 12 V на линии OBD» является упрощением.
- Существуют два разных механизма:
  1. **Активация Ethernet** (ISO 13400): обычно контакт 8 разъёма OBD подаёт сигнал пробуждения на сущность DoIP.
  2. **Пробуждение CAN‑шины**: классический wake‑up frame или изменение напряжения на трансивере CAN, связанное с зажиганием/клеммой 15.
- На практике оба часто связаны с включением зажигания, но они являются отдельными триггерами. Для VW MEB достаточно одного из них (обычно CAN‑пробуждения + UDP‑запроса) прежде чем шлюз начнёт отвечать на UDP Vehicle Identification Request.

## 4. Статья CSDN: «C++ DoIP配置未通过OEM验收的7个隐性缺陷（附TÜV认证级配置Checklist）»
URL: https://blog.csdn.net/LogicWander/article/details/160765860
### Семь скрытых дефектов
1. **Несоответствие формата VIN/EID требованиям OEM**
   - ISO 13400‑2: VIN = 17‑симв. ASCII, EID = 6 байт.
   - Некоторые OEM требуют определённый префикс в VIN (например, «WBA») или XOR‑контрольную сумму в последнем байте EID.
   - Вызывает ложные ошибки 0x0005 (Unknown Logical Address) и приводит к отклонению OEM.
2. **Гонка при маршрутной активации в многоканальной топологии**
   - Параллельные запросы Routing Activation Request (0x0003) к разным ECU; если ответ любого из них задерживается более параметра 0x0004 (по умолчанию 5 с), стек может преждевременно закрыть соединение.
   - Исправление: динамически увеличивать таймаут в зависимости от количества переходов (hop‑count), например, `timeout = 5000 + (hop‑2)*1500` мс.
3. **Нарушение синхронности состояний DoIP и UDS**
   - При получении Diagnostic Power Mode Request (0x0005) шлюз часто сразу посылает ACK, не дождавшись завершения перехода UDS‑state‑machine.
   - Последующий запрос Diagnostic Session Control (0x10) отклоняется с ошибкой 0x22 (conditionsNotMet).
   - Решение: блокировать ACK до подтверждения перехода UDS либо добавить механизм повторов с проверкой флага состояния UDS.
4. **Статическое привязывание портов vs. брандмауэр транспортного средства**
   - DoIP по умолчанию использует TCP/UDP 13400, но многие ECU не поддерживают динамическое согласование портов.
   - Брандмауэр транспортного средства может открывать только один протокол (часто только UDP) или фильтровать по сервисным портам UDS, игнорируя сигналы DoIP.
   - Необходимо проверять возвращаемое значение `bind()`, включать `SO_REUSEADDR` только после подтверждения правил брандмауэра, вести журнал отброшенных пакетов.
5. **Ошибочная интерпретация Alive Check в режимах низкого энергопотребления**
   - При выходе из Sleep‑режима ECU нуждается в стабилизации питания/тактов (15‑80 мс); ответ на Alive Request может задерживаться более обычного окна (~500 мс).
   - Шлюз, видя два подряд пропущенных Alive Request, может сбросить соединение.
   - Требуется реализовать адаптивный «период снисхождения при пробуждении»: увеличивать допустимую задержку Alive Response до 1200 мс во время wake‑up, управляя флагом низкопотребностного прерывания MCU.
6. **Требование к латентности парсинга заголовка DoIP**
   - OEM часто требует, чтобы среднее время обработки заголовка (поля ProtocolVersion, InverseVersion, PayloadType, PayloadLength) не превышало 15 мс (99‑й процентиль).
   - Следует использовать zero‑copy парсинг и избегать динамических аллокаций в горячем пути.
7. **Проверка согласованности VIN**
   - VIN, получаемый через UDS‑сервис 0x22 F190, должен точно совпадать с VIN, записанным в NVM ECU и передаваемым в DoIP‑сообщении VehicleAnnouncement.
   - Любое несоответствие ведёт к немедленному отказу.

### Чек‑лист уровня TÜV для конфигурации DoIP
- Проверить поля заголовка DoIP: ProtocolVersion = 0x02, InverseVersion = 0xFD, корректный PayloadType и PayloadLength.
- Подтвердить соответствие формата VIN/EID (ISO или специфические требования OEM).
- Убедиться, что латентность парсинга заголовка ≤ 15 мс.
- Настроить таймаут маршрутной активации в зависимости от глубины топологии (hop‑count).
- Синхронизировать состояния DoIP и UDS‑machine (никакого преждевременного ACK при 0x0005).
- Validate привязки портов TCP/UDP 13400; убедиться, что брандмауэр транспортного средства разрешает оба направления.
- Реализовать Alive Check с динамическим таймаутом, учитывающим latency пробуждения.
- Выполнить end‑to‑end проверку согласованности VIN (UDS 0x22 F190 vs. DoIP VehicleAnnouncement).
